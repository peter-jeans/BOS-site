Guided setup on Mac and Windows

Availability: the device launcher is an implementation candidate under testing. Downloads are held; this guide describes the intended reviewed flow. Use the manual Codex/Claude instructions until the setup page publishes the qualified download. Basic Windows installation and reuse have passed on a real Windows runner. Full first/second-project launcher and desktop-prompt acceptance are not yet verified.

  1. Prepare your account and backup. Sign in to My BOS, personally review the current terms and acknowledgements, select your actual coding tool and prepare its secure connection. Keep a recoverable project backup. Your free month starts at the first verified project, not at download or tool preparation.
  2. Download the complete setup folder. Use the published link and checksum on the computer setup cards. Extract the archive. Keep its launcher, setup.mjs, release metadata and inventory together. A checksum checks the bytes; use the trusted Cloud BOS publisher link.
  3. Open the right launcher. On Mac, open Start Cloud BOS.command. On native Windows, open Start Cloud BOS.cmd. The optional PowerShell entry point is Start-CloudBOS.ps1. Review normal OS prompts yourself. If your device policy blocks a script, use the manual route or ask your administrator; do not disable protection to continue.
  4. Check prerequisites. Node.js 20+ and your coding tool's supported CLI need to be available on PATH. The launcher points to official installation instructions when missing; it does not silently install or upgrade them. A desktop app can work while its CLI is unavailable. WSL has separate settings and connections; this launcher does not switch into it.
  5. Choose Set up BOS. Select Codex, Claude Code or both. Choose the exact app folder, including nested folders or spaces. An absent folder is created only after you confirm its path. Use separate physical folders/checkouts for Codex and Claude; a grouping folder is not automatically an app. Existing private BOS controls or conflicting installations stop for review.
  6. Review installation and sign in. Approve the displayed installation steps. The launcher verifies the exact package inventory and uses the native plugin manager. Complete tool trust and browser OAuth yourself. Supported OAuth routes do not require a pasted BOS API secret. Claude may require reviewing its bundled server in /mcp; a second external server is not added to force success.
  7. Open your project and approve its setup. The launcher can offer to open the coding tool at the exact folder with the onboarding instruction. Otherwise copy the displayed instruction into a new chat there. Review the project baseline and precise proposed files before approving. The existing BOS bootstrap owns .cloudbos/ and the correct host instructions, preserving existing text and imports. Installation alone is not project activation.
  8. Verify a useful result. Ask the tool to verify the live connection, exact project binding, saved control files and actual instruction loading. Do a small useful task, save it and return in a new session. Report missing behavior instead of assuming a printed header proves success.
What do Add a project and Check setup do?

Add a project reuses the plugin and account connection, then hands the new exact folder to the native project approval flow. It does not start OAuth again or restart the trial. If the native connection has expired, the coding tool diagnoses that separately and can ask for sign-in.

Check setup is read-only: it observes the tool/plugin version and folder state, then explains the next step. It does not repair files, create a folder, accept approvals or claim live access from a version label.

Existing setup, interrupted install or a conflict

Rerun the launcher to check incomplete steps. A matching verified local package can be reused. An existing Git installation needs exact-payload review; the repository URL and version alone do not prove integrity. Older, disabled, private, unknown or conflicting entries are preserved for review. No uninstall, credential reset or replacement happens automatically. If the tool saved part of the setup before an interruption, retain that state and follow the reported next step.

One coding assistant per project folder.

Choose one coding assistant for each project folder. If you use both Codex and Claude Code, give each its own separate checkout. Shared-folder use has not yet been verified.

A separate checkout is a different physical directory, not a second alias, shortcut or symbolic link to the same directory. Confirm each checkout’s exact project and BOS binding. Separate checkouts do not automatically create a supported shared BOS binding or make simultaneous Git changes conflict-free.

You do not need to flatten these folders, move the app or make a new Git repository for BOS. Open the app or package you actually intend to work on.

A parent project with child projects, or a monorepo?

Select the actual project or package explicitly. Its project root may differ from the repository root. Native instructions from ancestor folders can still apply, but a BOS identity or approval for the parent does not silently authorize a child or sibling. Confirm both the selected app/package and the scope of any proposed changes.

See how BOS uses project roots and control files. Grouping folders are not automatically projects. Adding another project uses the existing supported plugin installation; it does not require reinstalling BOS for each nested folder.

Starting from an empty computer or project folder

First check that the published BOS release supports your coding tool and operating system. These folder-preparation steps do not qualify a BOS installer on macOS or Windows. A missing or unsupported installer is a setup gap; do not copy replacement control files into your app to work around it.

macOS: create the folder in Finder

  1. Open Finder and go to the place where you keep your projects, such as Documents. Choose File → New Folder (or press Shift–Command–N).
  2. Name the folder for your app, for example MyApp. Open it. This is the project root you will select in your coding tool.
  3. Use your coding tool’s project/folder picker to open this exact folder. Check its displayed name and full path before starting work.

Windows: create the folder in File Explorer

Folder preparation only: a Windows BOS installation route has not been qualified by this guide. Proceed with installation only when your published release explicitly confirms the host and OS.

  1. Open File Explorer and go to your chosen projects location, such as Documents. Press Ctrl–Shift–N to create a folder.
  2. Name it for your app, for example MyApp. Open it and use the address bar to check its full location.
  3. In your coding tool, select that same folder using its project/folder picker. Verify the displayed root; do not select Downloads or the extracted plugin folder.

Using the command-line tool?

Open Terminal on macOS, or PowerShell on Windows. Change into the project folder before starting Codex or Claude Code. Replace the example path with your own; the commands below only select and show the folder.

cd "/ABSOLUTE/PATH/TO/MyApp"
pwd
Set-Location -LiteralPath "C:\PATH\TO\MyApp"
Get-Location

Check the printed path. Once the coding tool is installed and the release supports this route, start codex or claude from that terminal. The folder you launch from must be the intended app root. Complete one-time plugin installation and authentication, then connect and approve this project separately.

Keep the plugin separate

Store the downloaded archive, manifest and extracted plugin distribution outside MyApp, in a persistent tools folder. Follow the qualified release’s marketplace installation route; extracting a distribution is not installation. Your coding session points to MyApp. Keep both locations, and preserve the distribution’s hidden folders.

I already have a project

Back up the existing project. Open the existing app or package folder you intend to work on. In a monorepo this may be below the repository root. Do not accidentally create a duplicate MyApp folder inside it, move its source into the plugin distribution, or replace its existing instructions. Intentional nested projects are supported through explicit root and scope selection. For a CLI session, change into that existing root and verify the printed path before launching the tool.

If you are unsure which directory is the root, ask your coding tool to identify it read-only before approving setup.

Where do AGENTS.md and CLAUDE.md belong? Can one plugin serve many apps?

Install the plugin once for your user in each coding tool; set up each project separately. Choose user scope in Claude Code. The plugin and authenticated service connection can be reused across projects where enabled and permitted. They do not create a shared BOS project or make every folder active. Opening another project does not require copying plugin files or OAuth credentials.

Use the exact filenames AGENTS.md and CLAUDE.md, with the displayed capitalisation. Keep each app’s project instructions and .cloudbos/ records in that app’s selected root, alongside its source folders. Nested organising folders are fine:

App Development/                  ← organising folder only
├── App One/                       ← Codex project root
│   ├── AGENTS.md
│   ├── .cloudbos/
│   └── src/
└── Client Work/
    └── App Two/                   ← Claude Code project root
        ├── CLAUDE.md
        ├── .cloudbos/
        └── src/

Parent-folder trap: native ancestor instructions can apply to projects below them. Claude Code reads applicable ancestor CLAUDE.md files; Codex normally builds its project instruction chain from the detected repository root down to the working directory, and without a detected root checks the working directory. A parent’s BOS identity, baseline or approval never grants authority to a child app. Keep project-specific paths, bindings and approvals out of a shared organising folder.

Optional personal defaults in ~/.codex/AGENTS.md and ~/.claude/CLAUDE.md apply across your projects. Use those for general preferences, not one app’s BOS identity, installation records or secrets.

Existing files: preserve them. The approved BOS setup adds its managed instructions instead of replacing unrelated text. If Codex has a nonempty AGENTS.override.md, that takes precedence over AGENTS.md in the same directory, so setup must inspect it. Claude’s active instruction entry depends on its version and settings: the compatible route uses CLAUDE.md, importing a local shared AGENTS.md when appropriate. Newer Claude versions can read AGENTS.md directly in supported configurations, but an ancestor CLAUDE.md can change that selection. Do not assume every host loads both files or change global settings to force it.

For every new project, open its exact root, ask BOS to check its connection and existing setup, review the baseline and installation plan, then verify the saved files and current binding. Plugin availability, files being present and native instructions actually being loaded are separate checks. Keep Codex and Claude in separate physical checkouts as described above.

Interacting with BOS

How to tell you are ready

These are checkpoints to verify, not status readings from your account.

  1. Tool ready: the expected plugin or workspace skill is loaded and enabled; its version matches the published release instructions.
  2. Connection verified: the tool reports its actual authenticated Cloud BOS connection and names the intended project. Sign-in alone is not project activation.
  3. Project active: the approved changes have been reopened and verified. Look for project_governance_state: GOVERNED_ACTIVE and project_binding_verified: true, supported by current saved-file checks.
Then try one small piece of work. Confirm its result was saved, reopen the project and check BOS can resume from that record. If any checkpoint is missing, setup remains incomplete.

Get unstuck

I have not received a BOS email

Check your Spam or Junk folder. Sign in to My BOS to see your authoritative access and trial status without waiting for an email.

I cannot get a package or prepared connection

Check public release readiness. A pending download or listing is not an install link. Continue only after the reviewed package, manifest, checksums and matching instructions are published; no private invitation or manual package request is needed.

The package hash differs, or an install command fails

Do not continue with a mismatched archive or manifest. Confirm the exact published filenames and complete hashes. Check the separate host compatibility record for the verified installation route and any required path. Keep the persistent extracted folder. Report the failing step; do not substitute an older release or overwrite your app.

Sign-in worked, but BOS tools are unavailable

Confirm the plugin or Base44 connection is enabled in the current tool. Follow its reload instruction or open a fresh session, then finish any authentication prompt and repeat the read-only connection check. Keep passwords, tokens and private project content out of support messages.

BOS names the wrong app, or says it is not active

Stop before approving changes. Open the correct app or repository and repeat its connection check. Review the exact project setup plan if needed. An installed plugin is not proof of an active project; preserve any existing private or local BOS connection.

Setup paused at approval or Base44 AI Controls

Return to the same project and continue the pending stage. Use the exact currently verified instructions and plan, not a remembered hash or old screenshot. After saving AI Controls, reopen the field for the required independent readback. A “saved” message alone is not completion.
