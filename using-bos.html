Know what BOS
is telling you.

Ask for help in ordinary language. BOS brings project context and guidance into your coding conversation; your coding tool carries out the work. In existing verified Codex and Claude Code projects, request BOS explicitly for the current task. Automatic help and saved On/Off choices across sessions are still being implemented and tested as of 20 October 2026, including how those choices control activity recording. One-off help does not turn on continuous assistance.

Before you connect a local project

Your folders can be nested.

Keep the organisation that works for you. Create a folder for a new app, or open the existing folder for an app you already have. In Codex or Claude Code, select the actual project folder, even when it sits several folders deep.

Developer/
└── App Development/             grouping folder
    ├── Project Alpha/          ← open this project
    ├── Games/                   grouping folder
    │   └── Project Beta/                 ← or this project
    └── Business/
        └── Tools/
            └── My App/          ← or this project
One coding assistant per project folder.

Choose one coding assistant for each project folder. If you use both Codex and Claude Code, give each its own separate checkout. Shared-folder use has not yet been verified.

A separate checkout is a different physical directory, not a second alias, shortcut or symbolic link to the same directory. Confirm each checkout’s exact project and BOS binding. Separate checkouts do not automatically create a supported shared BOS binding or make simultaneous Git changes conflict-free.

One installation; a separate project connection. Select Project Alpha to work on Project Alpha. Select Project Beta to work on Project Beta. You do not need to flatten your folders or reinstall the plugin for each app.

These names illustrate a folder layout, not tested customer projects. Base44-native work happens in the selected Base44 app and does not need a local project folder.

What if a project contains another project or several apps?

A monorepo or an intentional parent/child project layout is also valid. Confirm which app or package the current task targets. Your tool may read instructions from parent folders; BOS should still identify the exact selected project and preserve its own binding and approvals. A parent or sibling project’s connection does not prove this project is connected.

After setup, ask the agent to show the selected root and the exact control files it saved. Codex normally reads AGENTS.md. Claude Code reads CLAUDE.md and, in current versions, can fall back to AGENTS.md when no Claude instruction file applies. BOS’s project setup must preserve existing instructions and verify its own saved files. Installing the plugin alone does not prove those files were created.

Inside a BOS reply

These are illustrative examples. Versions, wording and available fields vary by platform and installed release. Canonical BOS header and footer behavior is not yet qualified in native Codex or Claude Code; successful sign-in and project checks do not prove that formatting is followed. Expand each line for its meaning; these controls belong to this guide, not to your coding tool’s chat.

Example Codex conversation · illustrative values · not a live connection
BOS ! VER 1.8 AUTH ! DEV ! DBPP ! INT ! SCOPE ! CONF [-----] ROUTE:GENERAL

This is a compact status check for the current work. ✓ means verified for that check, ! means caution or partial evidence, and ✕ means missing, failed or blocked. A row of green checks is never a promise that every part of your app is correct.

BOS / VER
Whether BOS is available and the version supplying the guidance.
AUTH
Whether the required project and governance authority is currently bound. This is not simply “you are signed in.”
DEV
Whether the development context or pack needed for the work is current.
DBPP
Readiness for the current development stage. It is not a percentage of the whole product completed.
INT
Integrity of the checked BOS material.
SCOPE
Whether the current work matches the intended project.
CONF
Confidence in the available execution evidence; dashes mean unknown. This is not a model’s probability of being right.
ROUTE
The selected way to handle the request.
BIND:CURRENT_PROJECT_READBACK PHASE:build/PROVISIONAL EVIDENCE:NOT_VERIFIED CTX:example LDP:UNKNOWN ACCESS:UNKNOWN CONN:UNKNOWN GOVSRC:UNKNOWN AI_ROLE:UNKNOWN
BIND
How the conversation is tied to the current project.
PHASE
The assessed stage, such as planning or building. “Provisional” means the assessment is not final approval.
EVIDENCE
What has actually been verified. Saved source, a test and a working live app are different kinds of evidence.
CTX
A reference for the context read back for this response. It is not a password or permission.
LDP
The installed local development-pack mode, where that concept applies.
ACCESS
The declared context, such as owner or support. This label does not itself grant permissions or a paid tier.
CONN
The verified connection used for this work.
GOVSRC
Where the governing project guidance comes from.
AI_ROLE
The task duty selected for the agent, such as investigating or reviewing. It is separate from the model and from access rights.

UNKNOWN is an honest gap. Ask what evidence is missing and whether it affects this particular action.

BOS1.8> Codex> user>

The speaker chain identifies BOS, the active coding tool and the audience. A Base44 conversation uses Base44>; Claude Code uses ClaudeCode>. Specialist or committee speakers may appear when that workflow is actually used.

“The button label is saved. I checked the changed screen; the live mobile view still needs checking.”

The main answer should say what changed, what was checked and what remains uncertain. “Planned,” “saved,” “tested” and “deployed” mean different things. Ask for a focused check if a completion claim lacks evidence.

Actual model/reasoning: UNKNOWN / UNKNOWN

These are settings actually observed from the current host. If the tool cannot verify them, BOS should say UNKNOWN. This line does not choose or change a model.

Next self — CODEX (example project/chat): CODING / UNKNOWN (desired MEDIUM) — Make the approved button-label change. Recommendation only.

This is advice for the next task: which tool or capability, what reasoning effort, and why. It does not switch settings. A real handoff may have separate orchestrator and target rows. With no next task, the footer should say that a recommendation is not applicable.

What about install or publish footers?

Developer-facing replies may also show waiting installation work or a publication receipt naming the source, target and result. A Git push and a working runtime deployment are separate outcomes. Routine customer replies may not need these extra receipts.

Start with ordinary words

You don’t need to memorise commands.

Tell your coding tool what you want to achieve. Start small and name the project or screen. Copy a starter below, then add your own details.

Connect BOS to this exact project. Check its current setup and saved decisions first. Explain any proposed changes before making them.

Use BOS to review the problem I describe below. Show what the evidence supports, suggest the smallest useful fix, and tell me what needs testing.

Resume this project from its saved purpose, accepted decisions and current intention. Tell me what is complete and the next unfinished step.

Inspect first, approve a bounded repair

/scan and /scanfix do different jobs.

/scan: understand the findings

Ask BOS to inspect a named page, workflow or concern. It should confirm the project, source revision, supported scan and your access. Cloud BOS plans the scan; your coding host inspects the project.

Expect finding IDs, supporting evidence, severity, uncertainty, a proposed fix and a verification check. Missing source or untested runtime behaviour must remain explicit. A scan does not promise to detect every failure.

/scanfix: act on selected findings

Choose the finding IDs you want addressed. BOS should confirm they belong to the current scan and source revision, then show the bounded repair plan. A stale scan needs refreshing.

Your agreement to continue does not bypass exact project approval, backup or permission checks. The coding host applies only the approved work, reopens saved changes and tests the affected workflow. Ask what passed and what remains unresolved; no command guarantees every issue is fixed.

Which hosts and plans support these requests?

Availability depends on the installed BOS version, authenticated account entitlement, selected host and exact project binding. Base44 uses its connected builder tools; Codex and Claude Code use their verified local or public connection route. Local private BOS and public Cloud BOS do not expose identical commands. Ask the connected capability discovery what is available. If a slash command is not recognised, use the same plain-language request; this does not create missing tools or extra access. Public self-service native qualification is still pending.

Use tools when the job needs them

What works alongside BOS?

You don’t need every companion tool. Your chosen workflow determines which ones are useful; each keeps its own sign-in and permissions.

BOS plugin or Base44 skill — project guidance

Supplies BOS workflows and connects to Cloud BOS where supported. It does not grant access to all your other apps, install every companion, or make the coding agent infallible.

Base44 connector — direct access to an app sandbox

Lets an external coding tool work on the exact Base44 app you authorize. Its tools and account access are separate from BOS. Useful for the direct sandbox workflow above. Read Base44’s external-agent documentation.

GitHub integration — source and review

Moves reviewed source changes between the selected repository and supported app integration. Keep the app, repository and branch clear. Source sync does not equal deployment or proof that a feature works.

Computer control — visible setup and checking

Helps a coding agent navigate supported browser or desktop screens, inspect a preview and verify settings that have no suitable API. Availability varies by host; it may require a separate plugin and device permission. Use it when the task needs visible interaction. BOS installation alone does not install or authorize it.

A browser or testing tool — check the actual result

Useful for exercising screens, forms and navigation after a change. The agent should report which checks actually ran. A screenshot shows one state; it cannot prove every workflow works.
