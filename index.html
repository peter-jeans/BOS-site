How you use BOS

BOS works through your coding tool. You describe the task in its chat; BOS adds project guidance, and the coding tool carries out approved work and supported checks.

1

Connect your coding tool once

Add the BOS connection or plugin to Codex or Claude Code. Base44 uses an account connection and a skill in each workspace you select.

Expect: a loaded BOS connection and sign-in. Each project still needs its own setup.

2

Set up each project

Open the app or repository you want help with. BOS identifies it and proposes its project setup. You review the requirements and exact changes.

Expect: the correct project name, a plan to review, then a check of the saved result.

3

Ask for help with a task

Ask for a review, a fix or a supported feature. Some capabilities guide the development work; others propose code or settings for your app.

Expect: the proposed work, evidence from checks and anything still unverified.

You do not need to install these capabilities into a separate BOS application. Your project and chosen coding tool are the working context. See a first conversation.

For apps that keep evolving

Built for longer, changing apps.

For builders dealing with recurring breakages, important data, multiple user roles or organisations, and workflows that need to survive change. A small early prototype may need less of this support.

Where the extra structure can help
  • Permissions and boundaries: identify who can see or change each record, including across organisations, and plan checks under different user identities.
  • Correct rules and data flows: trace inputs through business logic to outputs; compare the rules used by screens, backend functions, scheduled jobs and integrations.
  • Saves that survive retries: check duplicate prevention, interruptions, retained history and recovery before relying on a workflow.
  • Continuity through change: recover available accepted decisions and unfinished checks from saved project records when work resumes.
  • Inspectable repairs: keep the changed artifacts, actual test results and remaining acceptance steps visible.
  • Platform fit: separate code checks from dated observations on the actual device, operating system and browser.

Your coding tool performs the work. Available BOS help depends on the tier, host and verified setup; these benefits do not make unfinished installation packages ready.

The problems

Four ways AI builds go off track.

BOS helps keep AI responsible as it builds.

  • DriftGoing off-plan. BOS checks changes against your agreed intentions.
  • AmnesiaForgetting decisions. BOS helps preserve project context between sessions.
  • HallucinationMaking things up—or saying “done” too soon. BOS asks for evidence.
  • BreakageBreaking what already worked. BOS helps check for regressions as your app changes.

BOS uses saved project records to help your coding AI pick up the work. It checks what those records actually say instead of relying on the previous conversation.

For example: Come back next week and see why a particular save method was chosen, what passed testing and what still needs doing.

You receive: A clear starting point, relevant decisions and the next unfinished task.

Plus: lasting project history. Basic project documents are part of setup. Pro’s planned ability to sync and restore across computers still needs verification.

Early Warning SystemSpot signs that your AI build is going off track, such as conflicting changes, forgotten requirements or fixes that haven’t been tested.See an example and availability

BOS helps identify problems while you build and explains why they matter. A warning may suggest checking a result, investigating a conflict or pausing a risky change.

For example: The AI says saving is fixed, but nobody has checked whether the information survives reopening the app. BOS keeps that missing check visible.

You receive: A clear warning, what prompted it and a suggested next step.

All tiers: basic safety warnings. Pro: advanced warnings and checks have passed local tests; delivery in each coding tool and effectiveness in real builds are still being tested. BOS cannot predict every failure.

Check That the Fix WorkedAn AI saying “fixed” is only a starting point. Define what needs testing and see which checks actually passed.See an example and availability

BOS helps turn a reported problem into a focused repair and test plan. Your coding tool runs the checks it supports; BOS helps keep the results and remaining gaps clear.

For example: After repairing saving, test reopening the app, invalid entries and a related screen to check that the change did not break something else.

You receive: What changed, what passed, what failed and what still needs checking in the running app.

Standard: basic test guidance and checks where the required tools are installed. Plus: retained test history. Pro: help coordinating more complex checks.

Check Platform FitFind features that may need a different approach on your chosen platform before spending time building them.See an example and availability

BOS helps identify platform limits and the device tests needed to confirm support. It can suggest a different design or a fallback when the original approach is unsuitable.

For example: Before building phone notifications, check whether they can work when the screen is locked—and test that behaviour on an actual phone.

You receive: The relevant limitation, what needs testing and a practical next step.

Standard: basic platform guidance. Pro: deeper planning across coding tools and assessment of a move to another platform. Support must be checked for your actual app and devices.

Learn from Proven FixesUse reviewed lessons from successful repairs to help with similar problems in another app.See an example and availability

A reviewer checks whether a lesson is suitable to share without private project material. Another app receives it only when relevant and must still test its own result.

For example: A retry caused duplicate actions in another app. A reviewed lesson can help you check whether your app has the same risk.

You receive: A relevant lesson, when it applies and the checks needed before relying on it.

Pro: in active testing; each app needs the appropriate setup. Shared lessons exclude raw source code, private conversations and customer data.

Expert AI ReviewBring specialist AI perspectives to a difficult change, helping you consider risks and options before proceeding.See an example and availability

A person supervises the review and decides what happens next. The aim is to surface concerns that one perspective might miss.

For example: review a complex change from security, usability and testing perspectives before building it.

You receive: additional perspectives, concerns and suggested checks.

Pro: being tested in Codex with human supervision. Equivalent specialist workflows have not yet been verified in Base44 or Claude Code.

Examples from our own projects · reviewed 20 October 2026

Practical checks from real development work

These three examples come from the founder’s own app projects, built with coding AI and BOS. Each shows a problem we worked on, the checks performed and what still needed testing.

You bring the idea and judgement. Your coding AI helps build it. BOS helps keep agreed decisions, important checks and unfinished work in view as your app grows.

5 August 2026 · Avoiding double-counting when a save is retried

The problem: An assessment app needed to save an accepted answer, its score and a supporting record consistently—even if saving was interrupted and retried.

What we did: We checked that retrying the same accepted answer would keep those records together without counting it again.

What we saw: In a local simulated test, the accepted answer produced one scoring event and one supporting record, even after two retries.

Still to check: Saving, closing and reopening the running app, and checking its saved history, still needed testing. This test did not assess how accurately the assessment measures student learning.

8 August 2026 · Keeping forecasts and alerts on the same rules

The problem: A forecasting app needed its forecasts, alerts and connected feature to use the same calculation rules.

What we did: We brought the calculation rules together and added checks for matching versions across those features.

What we saw: Checks of the published app files found matching calculation versions reported for the app and its background functions.

Still to check: Matching versions do not establish forecast accuracy or verify later releases. Device support needs its own checks.

A separate owner-reported iPhone test on 23 July observed notifications arriving with the screen locked and opening the app when tapped. That dated observation did not cover every device or OS; an app-owned notification history was still needed.

30 September 2026 · Checking a timetable before publishing—and keeping a way back

The problem: A scheduling app needed to check required approvals and information before publishing, while keeping a way to recover earlier work.

What we did: We added pre-publication checks, confirmation for the exact version being published, recovery into a new draft and checks for competing publish attempts.

What we saw: Local Safari checks blocked publishing when approvals were missing. A separate test timetable was published and recovered, and its exported data matched the expected test data. Separate tests checked competing publish attempts and protection of published results.

Still to check: These were local checks using test data. A real-school pilot and hosted-deployment checks were still needed.

BOS helps you and your coding AI build with clearer decisions, useful checks and better continuity. Early internal comparisons showed promising time differences. Its value depends on keeping that support proportionate: unnecessary process, setup friction or BOS defects can also slow progress.

About these examples and our testing

The wider review covers ten app histories from the same owner, plus development of BOS itself. These are internal examples rather than independent customer studies. The builder, coding AI and BOS all contributed.

In one July comparison, a simulated beginner workflow used approximately 3.8 times the recorded active build time of a BOS-assisted workflow. Different prompting and incomplete equivalent completion checks make this a preliminary result. These observations do not establish a general speed multiplier or total-project cost saving.

Some defects and unfinished checks also occurred while using BOS. A short advice-only comparison produced similar results with BOS enabled, disabled or absent. A matched whole-app comparison measuring the full work and cost to the same finished result has not yet been completed.

These cases do not certify an app’s security, prove the accuracy of its forecasts or assessments, or guarantee reliability. Capabilities and verification differ by coding tool and release; check the current setup guide for your environment.

Why does support differ between coding tools?

Guidance: BOS suggests work and checks; your coding tool carries them out. Local installation: additional BOS components in your project can inspect files or run supported checks. Not yet verified: we have not established that the particular feature works in that coding tool.

A Base44 app edited through a linked code repository uses the Codex or Claude Code setup for that work. Changes still need checking in the running Base44 app. Claude Code includes its VS Code extension; ordinary Claude web chat is outside these guides.

Some security and performance checks have been tested on specific Base44 apps. That does not establish support for all apps or other coding tools. Enterprise team features remain planned.
