What changes when you build with BOS?

Less context to reconstruct. Clearer reasons to pause. Better evidence before you call a change finished. Open a benefit to see an example, the output and its availability.

Keep changes aligned with your appDrift protection helps catch a small request turning into an unintended change of rules, data or scope.Explore drift protection

BOS checks the proposed work against the app's purpose, current state and agreed boundaries. Project history helps carry those decisions into later sessions.

For example: you ask for a simpler booking screen. If the proposed change also alters cancellation rules or access to bookings, BOS can flag the mismatch and narrow the work.

You receive: the specific mismatch, why it matters, and the next check or change needed.

Standard provides baseline review and safety checks. Plus adds persistent history and deeper drift validation. The checks your environment can execute are shown below.

Pick up where you left offProject memory keeps decisions, unfinished work and the reason behind your app's design available for the next session.Explore project memory

BOS uses saved project records to bring the specification, accepted decisions, build intentions and verification history back into view. It checks the current records instead of relying on chat recollection.

For example: return to an app next week and see why one save path was chosen, what has passed testing and which work is still outstanding.

You receive: a grounded starting point and a clear next action, with the relevant project decisions available to the coding agent.

Plus includes persistent project governance and remembered project history. Basic project documents are available in the setup workflow. Cross-computer sync and restore are separate Pro features whose delivery is still being verified.

See developing risks soonerEarly warnings make stale state, recurring regressions and missing proof visible while work is underway.Explore early warnings

BOS can identify risks such as an outdated starting point, conflicting edits, access-control concerns or a mismatch between saved code and the running app. Advanced build verification records the warning separately from the builder's claim and the independent check.

For example: the builder says a repair is complete, but the running app has not been checked. BOS keeps that missing proof visible and identifies the readback needed.

You receive: a warning, its evidence and an appropriate next step: pause, investigate, obtain proof or repair.

Basic safety warnings apply across tiers. The advanced warning and build-verification workflow currently falls under Pro and has local test evidence; host-specific delivery and real-world effectiveness remain under verification. BOS does not predict every failure.

Know what actually passedVerification separates “the AI says it is fixed” from inspected changes, test results and observed behavior.Explore testing and repair evidence

BOS narrows a broken flow into a checkable problem, defines the evidence required and records what passed. An equipped coding environment can run app tests and representative user journeys; a suggested check alone is not a result.

For example: after a save-flow repair, check that data survives reopening the app, invalid input is handled and the change has not broken a related flow.

You receive: a change-and-test record showing completed checks, unresolved issues and anything still awaiting live verification.

Standard includes baseline verification guidance and testing components where installed. Plus adds retained build evidence and history. Pro adds advanced coordinated verification. Every tier keeps basic safety checks.

Check the platform before committingFind out whether your chosen environment can support the behavior your app needs.Explore platform checks

BOS brings platform constraints into planning and identifies what requires a device test, a different design or a fallback. Design, security and data-ownership checks help keep the proposed solution coherent.

For example: before building a feature that relies on background location or phone notifications, identify the platform limits and the device evidence needed.

You receive: a requirement-specific constraint, a test or proof requirement, and a feasible next step.

Standard includes baseline platform guidance. Pro adds advanced environment coordination and migration assessment. Device support must be established for the actual app.

Carry useful lessons into the next buildCross-app learning can turn a verified repair into reviewed guidance for another eligible project.Explore cross-app learning

A verified outcome can become an abstract lesson about the problem, intervention and required checks. A governed reviewer decides whether it is suitable for reuse. Another app receives it only when the context fits and must verify its own result.

For example: a reviewed lesson about duplicate processing on retries could help another app check a similar flow.

You receive: a relevant pattern, its prerequisites and verification requirements. Collecting a signal alone does not prove that a lesson worked elsewhere.

Pro includes privacy-bounded cross-app learning. Its delivery is in active testing and needs the appropriate app integration. Shared learning payloads exclude raw source, private conversations and customer data.

Examples illustrate how BOS is intended to help; they are not claims that those particular apps have been tested. Feature delivery depends on your tier, installed components and development environment.

Standard — guidance, focused checks and baseline safety

Start with app intake and health summaries, gap detection, a project-specification template, manual build guidance, scoped prompts and verification expectations. Get explanations at a depth that fits you.

Design, usability, platform, security and code-structure guidance can inform the current task. Your installed tools determine which checks can actually run. Basic target, access, security and verification safeguards are retained at every tier.

You can use BOS manually on different projects. Standard does not include long-term cloud history, automatic scan orchestration or cross-project intelligence.

Plus — project memory, deeper checks and continuity

Keep multiple projects and their history: specifications, accepted decisions, unfinished build intentions, changes and evidence. Use saved preferences so BOS continues communicating in the way you need.

Deeper validation checks whether project records remain consistent, whether setup/change/verification steps have been followed, and which approved source governs a change. Evolution and governance-effectiveness reporting make progress and gaps visible.

Recovery planning and governance-memory backups require the appropriate project integration. Remembered project history is distinct from backing up app databases or restoring work on another computer. Plus does not include continuous unattended operation.

Pro — early warnings, reviewed learning and coordinated work

Bring specialist perspectives into a difficult decision, coordinate bounded work across available coding tools, and use deeper project intelligence. Advanced warning and build-verification workflows make risks and evidence visible during a build.

Cross-app learning captures verified, privacy-safe lessons for review and appropriate reuse. Portability and rescue capabilities help assess dependencies, plan a migration or scope the repair of a broken app.

The Pro tier also includes cross-computer capsule sync/restore, project dashboards and timelines, automatic scan recommendations and scheduled snapshots in its product scope. These are not all delivered by the current public plugin. Local memory reconstruction is in pilot; cross-host restore, unattended execution and feature parity need their own verification. Current specialist orchestration is attended.

Enterprise — shared policies, review and audit across teams

Enterprise extends the model to organisation policies, custom governance frameworks, reviewer access, audit trails, team administration, cross-team reporting and private integrations.

Planned: these require their own organisation features and verified delivery. The current public plugin can plan policy and portfolio checks; it does not itself enforce company-wide policy or certify compliance. Project metrics must remain separate from individual developer scoring.

How do tiers, installation and access work together?

Your BOS tier determines which capabilities you may access. Your development environment, installed components and verified project setup determine how they can be delivered. An included capability may still be in testing or unavailable in a particular environment.

There is one public plugin. Changing tiers does not require reinstalling the plugin or your project's governance. A recommendation to upgrade does not change your access. No tier grants permission to change or publish an app automatically.

Platform subscriptions, hosting and model usage remain separate. The setup guides will provide public installation destinations when released.

How will BOS work in your environment?

Your coding environment performs the edits and tests. BOS brings the applicable project context, checks and workflow. The same tier can therefore be delivered differently in each environment.

Local features need local installation. The Codex and Claude Code columns assume a project with the appropriate BOS Local Development Pack installed and activated. Connecting the public plugin alone does not install these components. Base44 here means its native AI app builder.

What do “guided”, “local” and “pending verification” mean?

Guided: BOS helps choose the right work and proof; the coding agent or an approved adapter carries it out. Local: an installed project component can inspect files or execute checks using the tools available there. Pending verification: the required evidence for that host or feature is not yet established.

A Base44 app edited through a linked repository uses the Codex or Claude Code route for that repository work. The running Base44 app still needs its own readback. Claude Code includes its VS Code integration; ordinary Claude web chat is outside these setup guides.

Specific Base44 security/optimisation checks have target-bound live evidence. That does not verify every Base44 app or establish equivalent execution on another host. Enterprise organisation features remain planned across environments.

Technical detail: what does the current public plugin expose?

The public plugin supplies seven advisory tools and a five-step project-governance lifecycle. Higher tiers add check-planning depth. These tool interfaces are one way to access BOS; they are not the complete list of BOS product capabilities.

2

Add the workspace skill

Open the workspace menu and choose Settings → Skills → Add skill → Start from scratch.

Skill namecloudbos-governed-build
ScopeSelected workspace

Use Cloud BOS during Base44 AI app-building work to assess the project, keep platform connection separate from per-app governance, require exact approval before governance writes, and verify changed artifacts without adding a runtime dependency.

Paste the name, description and instructions below into their matching fields, then click Add skill. Keep the supplied wording and confirm the skill is enabled.

Review the exact public skill instructions
  1. At the start of a new or resumed app-building request, use the Cloud BOS bos_connect tool and read platform_connection_state and project_governance_state separately.
  2. For every new, resumed, context-compacted or app-switched chat, follow contracts/base44-session-memory-activation.json. Never resume governed work from chat memory or a chat summary alone.
  3. Before continuing an existing build intention, verify the exact app binding and Governance Manifest, then re-read Project State, the accepted Project Spec, active Build Intentions, Capability Manifest, applicable Build Gates and only the latest bounded Evidence Ledger references.
  4. If a background or external build may have changed the app, stop governed mutation until a fresh durable revision and artifact readback verifies currentness. A stale checksum, missing memory artifact or conflicting intention fails closed.
  5. When a Cloud BOS result is actually consulted, begin the visible governed response with BOS<verified-service-major.minor>> Base44> user>. Resolve the version from the authenticated bos_connect result; never invent or retain a stale version.
  6. Do not use the BOS speaker when Cloud BOS was not consulted or its identity/currentness could not be verified. Speaker text is provenance for the response, not entitlement, mutation authority or proof that an app is governed.
  7. Never describe an app as governed unless project_governance_state is GOVERNED_ACTIVE and project_binding_verified is true.
  8. For an unbound app, use bos_project_discover and bos_project_governance_plan first. Show the exact current plan and stop for approval bound to its plan hash before any governance write.
  9. Use contracts/base44-governed-app-onboarding.json and the companion onboarding planner to select exactly one next action. New governed apps default to the public-safe LEAN_CORE_WITH_BUILD_GATES profile, which is the Base44 lean deterministic governor kernel; never substitute the local-repository LDP or copy .bos into the app.
  10. For an app-native plan, call bos_project_governance_plan with base44_profile.profile_id set to LEAN_CORE_WITH_BUILD_GATES, the accepted project_spec and build_intentions including active_id, and the exact app_id plus current expected_app_revision. Only the server-issued, anchored plan is approvable. The legacy three-file projection cannot represent this profile.
  11. For drift repair, request an explicit ROLLBACK plan with the canonical installed manifest text, all exact restoration artifacts and the current observed prior hashes. Verify every restored byte against the bound manifest. Never turn repair into an unapproved update. After host application, use the lifecycle readback helper with independently verified provider evidence and matching before/after application-source digests before calling bos_project_governance_activate.
  12. After the eight-artifact governance profile is activated and read back, plan the owner/admin Cloud BOS connection-plug indicator as a separate app-surface action. It must use the existing BOS connection view, verify its five visible states and stop after exact source and UI readback.
  13. Before declaring a governed app ready for Base44 BuildAI, inspect the native AI Controls custom-instructions pointer. If it is absent, stale, misdirected or unreadable, use the onboarding contract's separate alter_base44_ai_controls_pointer_via_assist action. Assist selects the bounded action but grants no mutation authority and is not an app slash command. After exact documents/AICONTROL.md and Governance Manifest readback, Codex or Claude Code must use host computer control to install the canonical pointer verbatim, save, reopen the native surface, verify exact text readback, and stop on mismatch or unavailable computer control.
  14. Do not reconstruct, shorten, substitute or locally invent a governance plan, manifest, binding or approval.
  15. Use the available Level-1 advisory tools before an app change when they match the request. Their results guide the build but do not independently authorize app, data, deployment, billing or governance mutation.
  16. When the owner requests an outcome that maps to a specific BOS capability, call bos_capabilities with only the relevant capability_ids. Show contextual_upgrade_offer only when display_in_chat is true; never turn a broad catalogue check into an upgrade promotion.
  17. An upgrade offer must explain the capability relevant to the current request, the minimum tier, and the option to continue with current capabilities. Respect SUPPRESSED_COOLDOWN and SUPPRESSED_DISMISSED, and never repeat or rephrase a suppressed offer.
  18. Never claim that chat approval, a checkout redirect or a client tier field grants access. Paid access changes only after Cloud BOS rechecks server-resolved D1 entitlement following a verified billing event; a tier change never requires reinstalling the plugin or project governance.
  19. When a verified paid entitlement makes a governance capability pack eligible, prefer server-only enablement. Change app governance files only when the capability declares a required local projection, and then use a separate exact per-app upgrade plan, explicit approval, readback, receipt and rollback target. Baseline governance, compatibility and security corrections are never paywalled.
  20. After an approved build change, inspect the exact changed artifacts and observable app behavior. Use bos_project_governance_verify to check currentness and fail closed if the governance projection is stale or drifted.
  21. Send only privacy-minimal project facts to Cloud BOS. Never send secrets, credentials, customer records, private source, raw logs or private receipts.
  22. Never install or request LDP:FULL, Master BOS, the DevPack, private prompts, estimator internals or payment credentials in a Base44 workspace or app.
  23. Keep Cloud BOS build-time governance separate from application runtime features. Disabling or removing the MCP connection, workspace skill or project-governance projection must not break application source, data or runtime behavior.

Set up governance for a project

Do this separately for each app or repository, after connecting your development tool. Cloud BOS prepares a plan first; you decide whether to apply it.

Ask for a plan before changes

Use Cloud BOS to discover this exact app or repository with bos_project_discover, then prepare its current setup plan with bos_project_governance_plan. Ask me for any missing project specification or build intention. Show the exact proposed files, permissions and rollback or removal boundary, together with the current plan hash. Stop for my approval before writing anything. If governance is already active, verify it and report any drift instead of reinstalling.
  1. Check the exact app or repository, intended work and proposed changes. Approve only the current plan and its plan hash. If the plan changes or expires, review a fresh one.
  2. Let your coding tool apply the approved plan and reopen the exact files it changed. For Base44, the native AI Controls step needs Codex or Claude Code with computer control: save the approved pointer, reopen that app's AI Controls and verify the exact saved text. If that access is unavailable, app setup remains incomplete.
  3. Have Cloud BOS activate and verify the installed result. A governed project must report project_governance_state: GOVERNED_ACTIVE and project_binding_verified: true. A successful connection alone is insufficient.

On later sessions, ask to use Cloud BOS and check the current project before work. If sign-in, binding or verification fails, resolve that status before relying on governed changes.

Disconnecting or removing governance

Disabling a connection or plugin stops that tool from using Cloud BOS. Removing a project's governance is a separate, reviewed operation: request a removal plan for that exact project, approve its scope and verify the result. Application source, data and runtime behavior must be preserved.

What this installs—and what it does not

Cloud BOS stays in the build-time guidance layer. It does not become part of your published application.

Available while building

Your coding tool can use Cloud BOS to assess a project, plan checks and verify its governance while you build.

Scoped to your setup

Base44 uses an account connection and a skill per selected workspace. Codex and Claude Code use a plugin. Every governed project has its own approved setup.

Not full private BOS

No private project source, secrets, full project memory, private prompts or internal development pack is installed.
